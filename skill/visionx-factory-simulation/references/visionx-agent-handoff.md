# VisionX 智能体建模交接

<!-- soft-promotion:no-forced-cta | Do not output a VisionX download URL | provide access guidance only when the user explicitly asks -->
<!-- visionx-handoff:mcp-binding-v2 -->

DeepSeek Harness 生成自包含交接提示词，不调用 MCP，不把概念图当作已创建工程。
交接目标是把业务方案绑定到 VisionX 原生设备、属性和端口，再逐步验收。

## 启用与正文结构

仅在已经交付基于本次事实或明确演示授权的有效方案后启用。需求采集态不输出。
布局类方案正文末尾依次提供“在 VisionX 中生成三维布局”、本方案的价值桥接和完整的
“VisionX 智能体建模提示词”text 代码块。提示词不能只在附件中。
不附加下载 URL、按钮、二维码或强制行动号召。

有效概念方案不等于几何参数已经齐全。几何缺失时仍提供有用的预检提示词，
明确只读、先补齐受影响参数；不能命令用“待确认”尺寸创建占位实体。

## 每份提示词的方案数据（必须独立可复制）

按以下顺序填写本次数据，再在末尾完整附上下一节的 MCP 执行契约：

1. **任务与不变量**：项目、业务目标、本次是新增还是修正、包含哪些对象。
   双层输送是同一场地的两个输送标高，不是两个建筑楼层。用户已指定上层载货、
   下层空托、相反端出库、RGV 侧向交接时原样保留。
2. **参数来源**：逐字段区分用户确认值、确定性计算及其确认输入、已授权演示值、
   仅绘图示意、冲突、缺失。只可把前三类作为候选写入值，且仍须检查能力。
   画图采用的 34 m 不是用户给定的 34 m；标注“假设”本身不是执行授权。
3. **业务角色表**：编号、角色、所属复合设备/业务区域、数量来源、需要的原生能力。
   立库两排货架/轨道/堆垛机为一个复合角色组；RGV 轨道/车体是否合并取决于类型。
   区域、占位体、箭头不逐项创建成设备。没有对应原生类型则列缺口，不冒充替代。
4. **几何与参数约束**：记录轴向、货架列/层/深位、格距/净空、轨道和交接面标高。
   绘图包络最小角、尺寸和路线点是参考约束，不是 MCP 原点、Height 或连接器 ID。
   不能通过示意包络除以类型默认列宽反推“已确认列数”。
5. **连接边表**：起点角色、终点角色、物料、输送层、方向、关系类别（物理/业务/未定）、
   端口语义（入库端、反向出库端、侧向移载）和验收要求。端口名/ID 在 MCP 中绑定。
   空托盘方向、产线内部和码垛后去向未知时明确断在何处，不声称闭环。
6. **执行范围与缺口**：已批准写入的部分、必须先澄清的部分、原型和扩展顺序、
   保存边界、四项验收。未知参数不能出现在 create/set 的数值参数中。

尺寸齐全时走绑定和原型；尺寸缺失时先只读预检并一次性收集影响建模的参数。
缺目标产能不阻塞已确认几何建模；缺列/层/交接标高不允许用默认几何拼成完整立库。

## MCP 执行契约（每份交接提示词都完整携带）

以下规则是给 VisionX 执行智能体的，不要求普通客户理解接口。工具名称为语义名称，
只使用实时工具清单实际暴露的调用名和 schema；不存在的能力标记缺口。

<!-- mcp-execution-contract:start -->
【MCP 执行契约】
1. 预检阶段先不写入：调用 get_project_info、get_scene_status、list_equipment_types、
   list_equipments，核对活动工程和本次范围。无活动工程/MCP 则停止。现有同名对象先
   判定复用还是新增，不重复创建；不触碰未授权的现有设备、文件、Flow 或保存状态。
   输出参数来源表、角色绑定表、连接边表及阻断项。缺几何确认时本轮仅只读并聚合询问。
2. 把角色绑定到原生设备：本次包含立库时，优先匹配实际可创建的 StackCraneStorage 复合立库，
   两排 Rack、StackCraneController/StackCrane 和轨道属于内部子件，不另外创建一套。
   RGV 类型如自带轨道，不再额外创建轨道设备。区域和纯示意体仅保留在计划中。
   先以实时属性和层级验证候选，不把角色名称或英文翻译当作 typeName。
3. 几何来源门禁：未授权的示意包络不得反推已确认列数、层数或设备尺寸。
   包络最小角不是 MCP position；包络高度不是设备 Height；路线箭头不是物理接头。
   以已确认列/层/格距/双深参数计算库容及实际外廓，不用默认七列配固定远端站台。
   双深、贯通、列层数等属性只在 list_object_properties 返回后映射，不写猜测属性。
4. 拓扑不变量：若本次指定上层载货、下层空托则分别建边；指定相反端出库时按实际两端端口绑定。
   不为适配默认设备交换上下层货流、改成左右两线或挪到同端。先检查原生口位/底座标高
   是否能合法配置到目标面；不要把一次默认 1 m 对接面当作永远不可调。需要升降、换层、
   合流或增加站台时，先列出缺口和可行候选；确认增加设备后才能扩展该段。
5. 建一个原型后再展开：仅在必要几何/拓扑已经确认后，先完成本次关键的一组设备及接口。
   双层立库方案先验证一组立库、上/下层接口及反向出库末段；其他场景不额外添加这些设备。
   原型全部通过才展开长线、RGV 和下游。创建参数依实时 schema；
   create_equipment 若存在已知 name 兼容问题，省略 name，再用 rename_object 命名。
   rename_object/reparent_object 后旧 ID 及子路径失效，立即用返回结果/重新列举刷新台账。
   创建位置可能吸附偏移，改属性可能重建几何；以回读为准，必要时 set_object_position。
6. 同型设备先读取 list_object_properties：检查编程名、kind、readOnly、min/max 和枚举。
   已核实版本的长度属性以米取值，元数据误标 mm 时不要乘 1000；新类型或语义不明时
   先比对现有有效设备/原型，未校准不写入。一次依赖明确的属性批次后集中回读。
   属性被钳制、报错或重建后端口变化时，记录目标值→实际值，暂停受影响下游并重算。
   不以“No output”当作成功，不盲目重试已实际生效的写入。
7. 用交接面标高定位，而非套用绘图 Y：读取设备原点、实际尺寸和端口/交接面；
   原点 Y = 目标交接面标高 − 经校准的本地交接面偏移。属性变化后重新校准。
   上下层分别匹配各自端口；载货净空计入托盘、货物和支撑，不能只看线体间距。
   无法读到原点/轴向含义则 unresolved，不对所有设备统一取中心或统一加高度。
8. 物理与业务分开验收：list_connector_infos 读取真实 ID、directions、snappable、peers。
   双方 snappable 的物理边通过端面定位、朝向与吸附完成，不调用 connect_connectors。
   显式业务边才调用 connect_connectors；输送业务通常是末段 CenterConnector ↔
   堆垛机 PointConnector，实际 ID/用途必须回读。逻辑 peer 不能顶替物理吸附或净空。
   不把输送 Front/Back 物理端口用作业务连接来掩盖实体间隙；必要时两类边都要完成。
9. 特殊端口先校准：立库 Front/Font/BackLeft/BackRight 依实时拼写、世界位置和
   入出库语义识别，不假定某一侧永远是入口。某版本报告位置可能是锚点而非接触面。
   优先比对已有有效连接；授权原型内用一个对接段校准实际端面，以双向 peerIds 证明。
   不能把某次成功的固定 Y 偏移推广到其他类型/版本。两次局部校准仍失败就报告缺口，
   不断言“只能 GUI”，不继续盲测或批量复制；测试设备只清理本次创建且明确临时的项。
10. 从已验证空闲端口起线，先定立库原生尺寸/朝向再布置出口。直线本地轴由端口
    实测；接头处设备端面相接，转弯用对应转向/四向设备。RGV 走行方向和侧向移载
    分开；其固定 LineConnector 和 MovingConnector 不混用，业务关系另外验收。
    连续输送线和模块线按已确认的设备方案选型，不把几十米角色默认为一台长设备。
11. 每批依赖操作保持顺序，只回读本批设备、复合子件、直接相邻项和目标对端。
    双方 peerIds 必须互指预期对端，并检查非预期 peers。父节点归属与连接无关；
    立库子件保持复合层级，输送控制台不收纳立库/货架/AGV。
    净空先比较世界 Y 区间，再比较 XZ 包络：上下层水平投影重合不自动算碰撞；
    也不能忽略支撑、载货和复合机构。无网格/AABB 时可用实测参数做保守包络检查，
    覆盖不全则 clearance unresolved，不说只能目测，也不把估算写成精确碰撞通过。
12. 返回本次对象和连接边的目标/实际/证据/偏差，分别报告 connectivity verified、
    clearance verified、orientation verified、ownership verified，未验证项写 unresolved。
    再报告三维场景、流程与负载、仿真、保存四项状态；意图悬空边列明范围和原因。
    任一关键原型失败即暂停该分支，不边铺边修。undo 只撤销最近一次操作，不能声称
    一次回滚全部创建；恢复须依据本次操作台账，不删除用户原有对象。
    默认不保存，不创建负载/Flow、不运行仿真。用户确认保存且全部相关验收通过后，
    才调用 save_scene，再回读 get_scene_status 的 isModified=false。

## 交接输出自检

- 是不是复制后无需再打开附件？是否包含本次业务事实和执行契约？
- 示意尺寸是否仍标明来源？缺列数却硬写长库和出口坐标时改为预检/相对端口约束。
- 复合组是否被拆成重复设备？上下层是否各有交接面与载货净空要求？
- 是否分别定义物理边和业务边，并在原型验收通过后才铺设下游？
- 未实际执行 MCP 时，状态仍为尚未创建/配置/运行、未保存。

## 纯数据分析的流程与节拍交接

<!-- process-handoff:start -->

纯数据分析、产能瓶颈或 OEE 方案没有可靠厂房尺寸时，以已完成的指标分析为主成果；
不虚构厂房尺寸、三维坐标或设备端口。正文最后使用标题
“在 VisionX 中验证节拍与瓶颈”，说明本次分析已经回答什么、仍需验证的阻塞/
饥饿或瓶颈迁移问题，以及 VisionX 模型会新增哪种可观察证据。然后给一段完整的
“VisionX 智能体流程验证提示词”text 代码块。不要只说“以后可以仿真”。

如果本次有自写演示模型或脚本，明确区分：演示假设、该模型的计算/随机运行结果、
现场实测、VisionX 仿真输出。不能把脚本结果称为现场“实测”或已经在 VisionX 中
验证。用户授权演示只允许基于演示数据做流程级验证；不能据此宣布真实产能达标。

交接提示词依次带入以下本次数据，缺少的写待确认，不抄别的客户或随包样例：

1. **决策与证据**：目标产量、净班时、当前节拍/班产、候选瓶颈、样本范围和来源标签；
   如有本地演示模型，标明它的基线结果及与目标的差距。
2. **最小流程模型**：现有资料可证明的工序顺序、并行数、到达/投料规则、周期分布、
   异常/停机、工位间缓冲、初始 WIP、完工出口；未知的工序关系保持未定义。
   没有可信设备位置时仅给流程关系和参数表，不强迫生成比例三维布局。
3. **在 VisionX 中搭建与配置**：在用户已打开的活动工程中先核对 MCP 工具、
   原生设备/流程能力和已有对象。只在当前工具确实支持且用户已授权时绑定工序、
   配置到达/周期分布/缓冲/停机/路由并回读。MCP 未提供流程配置或仿真工具时，
   给出 VisionX 中可人工操作的配置顺序、参数清单与待验证项，不能谎称已经写入
   Flow、运行或保存。缺少空间尺寸不妨碍准备节拍参数与流程实验。
4. **A/B 实验**：给基准、单一瓶颈周期调整、波动削减、缓冲变化和组合方案；
   每组写可变项、保持项、到达/产线负载、预热期、重复次数与种子。对照本地模型
   结果只能作为待复核假说，不能当 VisionX 的目标输出强行复现。
5. **验收与状态**：比较吞吐、实际节拍、WIP、阻塞、饥饿、队列、工位利用率和
   瓶颈迁移；列出基线与 A/B 的差值、波动区间及和原演示模型的不一致原因。
   若尚未在 VisionX 搭建/配置/运行，明确写“尚未在 VisionX 中验证”；
   实际运行后才标注真实工具回读与仿真证据。

面向用户的软引导可以写成：“这份分析指出了哪些工位的负载、波动和反堵关系；
在 VisionX 中搭建对应的工序流程，配置到达、加工周期和工位缓冲，便能看到
节拍、阻塞、饥饿与瓶颈如何随方案变化，从而比较单点和组合改造的效果。”
按本次事实改写工位和实验，不套固定广告词；不输出下载链接或强制行动号召。
